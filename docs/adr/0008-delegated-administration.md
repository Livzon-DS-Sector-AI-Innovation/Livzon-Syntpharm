# ADR 0008: 委派式权限管理（Delegated Administration）

## Status

Accepted

## Context

权限体系此前只有两级：超级管理员（全部权限）与普通用户。所有角色创建、授权操作都集中在系统管理（/settings/permission），由超级管理员或持有 `platform:role:manage` / `platform:grant:manage` 的账号完成。随着业务模块增多，超级管理员成为瓶颈：每个模块的日常授权（谁能看偏差台账、谁能审批）都要找超管。

需求：超级管理员能为每个模块指派**模块负责人**（module owner），负责人在模块内拥有全部权限并可自行管理该模块的角色与授权；负责人还能指派**模块代表**（delegate），代表拥有模块内全部权限、可授权普通用户，但不能指派或移除其他代表。

现有守卫（`guard_manage_target` 的严格子集判定、`assert_actor_can_grant_role` 的权限包含判定）无法实现这一区分：代表的总权限集 ⊇ 另一代表的总权限集，严格子集成立，代表 A 可以移除代表 B；同理代表可以授出代表角色。「授予权限」与「任命代表」在现有模型里无法区分。

## Decision

引入**角色级别**（role level）作为授权守卫的核心概念：

| 角色 | 级别 | 内容 | 指派者 |
|---|---|---|---|
| `super_admin`（既有） | — | 全部权限（is_superuser 放行） | 系统内置 |
| `{module}:owner` | 2 | 该模块全部权限码 + 模块内授权/角色管理码 | 仅超级管理员 |
| `{module}:delegate` | 1 | 该模块全部权限码 + 模块内授权码 | 超级管理员或模块负责人 |
| 模块自定义角色 | 0 | 仅 `{module}:*` 权限码 | 负责人与代表均可创建/编辑 |
| 全局自定义角色 | 0 | 任意权限码（可跨模块） | 超级管理员（既有能力） |

规则：

1. **级别守卫**：创建/修改/移除某级别角色的授权，操作者必须持有同模块更高级别的角色（或超管）。负责人（2）管代表（1）与普通角色（0）；代表（1）只能管普通角色（0）。
2. **自动角色**：`{module}:owner` 与 `{module}:delegate` 由代码注册表按业务模块自动生成，随注册表新增权限码自动扩量（启动时同步）。
3. **模块作用域**：负责人/代表调用角色与授权 API 时，结果按模块过滤；创建模块角色时后端拒绝 `{module}:*` 以外的权限码。
4. **模块配置页统一**：每个模块统一设立 `/{module}/settings`（模块配置）页面并出现在侧边栏；既有零散设置页（如 `/hr/system/settings`、`/quality/instrument/settings`、`/quality/stability/settings`）的内容迁移进入该页。模块的权限管理（角色 + 授权）作为该页的板块，复用全局角色管理/授权管理组件按模块过滤。页面与权限管理入口由权限码 `{module}:admin:read`（含于 owner 与 delegate 角色）按既有侧边栏 + 页面守卫模式控制；页面上的配置项归属模块权限，不再使用 `platform:config:read` 这类平台权限守卫（该守卫是「只有平台管理员做配置」时期的遗留）。
5. **可见性**：模块角色同时出现在全局角色管理（/settings/permission?tab=roles），超级管理员可查看/编辑/删除，作为兜底。
6. **多负责人**：一个模块允许同时有多个负责人；负责人之间不能互相移除（级别守卫：平级不满足「更高级别」）。
7. **无数据范围特例**：负责人/代表拥有模块全部数据；数据范围（scope）机制当前无任何模块使用，本设计不引入范围化的行政权限。
8. **超管保底升级为「最后两名」**：移除或停用超管授权时，若操作后活跃超管少于 **2** 人则拒绝（原为「最后一名」）。原因：唯一超管的账号一旦丢失（离职/锁定），系统将无法恢复管理权——只有超管能授出超管，守卫本身会挡住恢复路径，只能动数据库。保留两名超管是防锁死的最低冗余。
8. **废弃角色档位**：全局角色创建表单移除「角色档位」（admin/operator/approver/viewer）下拉——该后缀自 2026-10 内置模块角色下线后不再有任何语义；角色编码改为自由格式。

9. **权限模型确认**（对照现有实现逐条核验）：同一用户可持多个角色、权限取并集（既有）；权限只能经角色授予用户，无直接授权（表结构保证）；角色权限变更在**下一次后端授权判定**时生效（查询时解析 + 缓存驱逐，Redis 缓存 ≤60s 兜底过期；前端不主动踢出已打开的页面，下次请求/刷新时按新权限渲染）；新增权限码时负责人/代表角色自动扩量、自定义角色不变（同步只增不减）；角色删除时其授权行一并**停用**（grant 置为 disabled，列表干净、可恢复——改变当前「角色软删后授权成孤儿行」的行为）。

配套变更（同一会话决定）：菜单可见性从「无权限即隐藏」改为「灰显 + 锁图标，点击进入无权限页」；模块管理入口同样适用。无权限时页面与后端 API 双重拦截：前端导航灰显，直连 URL 由模块 layout 守卫渲染无权限页，API 由绑定中间件 fail-closed。

## Consequences

正面：
- 模块日常授权不再依赖超管；超管只负责指派负责人。
- 级别守卫用一个小概念（整数级别）同时封死「代表移除代表」「代表授出代表」两类越权，无需通知/审批流。
- 模块管理页 ~70% 复用现有组件，改动集中在后端守卫与 API 作用域过滤。

代价：
- `roles` 表新增 `level` 列与迁移；注册表需生成每模块两个内置角色。
- 角色/授权 API 增加按模块过滤逻辑，全局视图与模块视图共享受损于过滤参数。
- 负责人权力集中（模块内无制衡），依赖审计日志与超管兜底；代表编辑角色会追溯性改变所有持有者权限，由审计日志记录、负责人审查承担。

## Alternatives Considered

- **纯子集守卫（不加级别）**：无法区分「授予权限」与「任命代表」，代表可互相移除。拒绝。
- **代表仅可授权、不可建角色**：代表实用性大减，模块内新角色需求仍要回到负责人/超管。拒绝（用户明确选择代表可建/编角色）。
- **模块管理页放系统管理下用模块切换器**：与「模块配置页在模块内」的统一约定（本 ADR 确立）不一致。拒绝。
- **模块配置页沿用平台权限守卫**：`platform:config:read` 会把平台级权力泄漏给模块负责人，或迫使负责人/平台管理员双权限共存；改为模块级权限码直接守卫。拒绝。
- **菜单无权限继续隐藏**：用户明确要求「看到页面存在、点击提示无权限」。拒绝。
